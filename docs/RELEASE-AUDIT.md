# Release audit: every way this can fail

Started 2026-11-05. One page per aspect, each item a failure that can actually happen,
not a checklist of virtues. Status is one of:

- **FIXED** — a defect that was found, with the commit or file that closes it.
- **OK** — checked and found correct, with what was checked and where it was read.
- **OPEN** — known, not yet closed. The rows that remain are marked *by design*: a decision, not a
  fault waiting for someone.
- **EXPLAINED** — reported as a defect, investigated, and found to be the code telling the truth.
- **UNKNOWN** — plausible, not yet investigated. There are none: every one has been read and answered.

This is the map. The design it audits is `docs/ARCHITECTURE.md`, and the decisions it
implements are in `docs/adr/`.

## 16. The tailnet route, audited separately (2026-11-06)

The radios got most of the attention in this pass; this is the same audit for the
route that is used every day. Verdict first: **the protocol and the payload are right for
the medium, and the only thing worth changing is one measurable inefficiency.**

| Aspect | Finding |
|---|---|
| Encoding | JSON control messages and binary output frames. **Protobuf would be a net loss**: the hot path (terminal output) already crosses as a raw binary frame with an 8-byte header, control messages are low-rate and small (an `input` message is ~60 B), and end-to-end `permessage-deflate` at level 3 is already negotiated on both ends (7.1x on repetitive output, ADR-0019). A binary control encoding would save tens of bytes per keystroke — below RTT noise on a tailnet — and cost the additive-wire property and the ability to read the protocol in a log |
| Snapshot payload | A JSON envelope around the pane text, measured 45.5 % larger than the raw text (4.2 KB → 6.2 KB on a live `RCNT` shell) because of escaping, and sent once per attach or resync, not per frame. Deflate absorbs most of it. Correct as it is |
| Latency | `TCP_NODELAY` set at accept, and keepalive probes at 15 s idle / 5 s interval / 3 misses. Keystroke echo is one message; the daemon holds a waiting `Peek` on the keeper (answered the moment a byte arrives, so the wait adds no latency), and the phone paces frames at RTT/2 bounded to 33-150 ms |
| Auth | Bearer token from the `Authorization` header only (verified live: no token 401, query token 401, header without upgrade 400, unknown path 404), constant-time comparison, tailnet-or-loopback peer check before the token, 64-connection cap enforced **pre-auth** with 503 |
| Frame limits | Frame, message and inflate expansion all capped; an unknown-length deflate cannot expand past the message cap; a bad upgrade is a 400, not a dropped connection |
| Flow control | One bounded queue per subscriber; overflow drops the subscriber and forces a resync rather than growing memory; snapshot fencing stops the tail being painted twice |
| Resync | `inplaceResync` when the client advertises it, full snapshot otherwise; epoch ordering keeps a stale frame from landing after a newer screen |
| Reconnect | Shared backoff with full jitter, capped at 256 s; `Rejected` is terminal until re-pair |
| **Watched poll** | A **watched** session asked the keeper 100 times a second, one socket call each: 8.2 % of a core in the daemon and 4.7 % in the keeper with nine desk windows open (measured 2026-11-06), and 9.7 % in the daemon with nine or ten open (2026-11-07). | FIXED, measured end to end. `Peek { wait_ms }` holds the call open and the keeper answers the moment a byte arrives, because `OutBuf::push` notifies a waiter registered on the buffer itself. The wait adds no latency (it ends on data), the sleep between passes stays at the old 10 ms so an echo is not delayed, and a quiet watched shell costs one call per 110 ms. After the keeper was restarted onto this code (2026-11-07 16:37), with the same ten panes and nine desk windows: **daemon 1.33 % of a core and keeper 1.07 %**, against 9.7 % before. The keeper honours the field as designed: `waitMs=0` answers in 0.1 ms, 300 in 300.9 ms, 600 in 501.5 ms (clamped to `PEEK_MAX_WAIT_MS`). Additive both ways, so an old keeper ignores the field and answers at once — that is the old cadence rather than a hot loop. Pinned by tests: a push wakes a waiting peek, and a wait does not delay a snapshot of the same pane. The gate is held across the wait, bounded at 100 ms |

### Risks that remain

| # | Risk | Evidence and mitigation |
|---|---|---|
| R1 | **A direct path has no per-hop recovery.** One lost hop costs an end-to-end retransmission at `6 airtimes × hops`, and five of those end the session. The community firmware's per-hop resend (`max.resend 2`) measured 71 → 95 % delivery on the same topology | `crates/session/src/arq.rs` (RTO), `docs/AIRTIME.md`. **The design space is closed, not merely inconvenient**: `RAW_CUSTOM` is delivered only on a direct route (`Mesh.cpp`), so a record cannot be flooded, and a repeater cannot resend what it forwards once. Path quality is therefore the only lever, which is why route adoption (6.176/6.188) is the whole game. `crates/session/tests/lossy_multihop.rs` now measures a 28-hop route with one record in five lost |
| R2 | **Discovery is a flood, and a flood costs one transmission per repeater in range** | Bounded: only while pathless, backoff 5 → 40 s with jitter, and the host asks only when traffic has moved in two minutes. `build_route_reply_flood` |
| R3 | **Repeater policy can silently cap discovery.** `flood.max` is 64 by default, but Canada's guide sets **16**, some meshes set `flood.max.unscoped 3`, and an advert is dropped at **8** | `RoutingPolicy.h`, `examples/simple_repeater/MyMesh.cpp:970-972`. Nothing can be done from the ends; the host log shows the hop count a request arrived by, which is the diagnostic |
| R4 | **Path widths can differ between ends** (host 1 B, a phone's radio 2 B). Legal, and interoperable only through repeaters on firmware ≥ 1.14 — older ones drop multi-byte packets unheard | `docs/ARCHITECTURE.md` §11; `PublicPreset.appliedPathHashSize` is what ldmux writes |
| R5 | **A site's private region scope cannot be named**, so a request under it is answered unscoped and may be dropped by `region denyf *` | `reply_scope` in `crates/daemon/src/mesh_serial.rs` |
| R6 | **Links are asymmetric.** A path heard one way is not a path that works; the phone once held a 0-hop ghost beside a 5-hop truth | `routeProven` + `failedRoutes` (10 min, four paths). Rows 6.159/6.160 |
| R7 | **Airtime is the scarce resource**: 602.6 ms per 172-byte record at 62.5 kHz. Metered bands get 36 s/h (1 %); this band has no limit, so the meter is a measurement and the discipline is ours | `docs/AIRTIME.md`, `ldmux mesh status` `airtime` line |
| R8 | **The session lives in the app process.** A foreground service and a partial wake lock hold it while a shell is **wanted** — including through a link failure, which is what lets the rebuild run in a pocket — and they are released on `Idle`, on a host that closed the shell, or after `LINK_GIVE_UP_MS`. A process the platform freezes anyway cannot recover alone; returning to the screen rebuilds at once | `MeshTerminalScreen.kt`, `BackgroundSession.android.kt` |
| R9 | **The phone's log is in-memory only** (a deliberate privacy decision) and logcat rolls over in about ten minutes of traffic. | R10 | **Five open shells is the ceiling** on the pager, refused with a sentence | `MAX_OPEN_PAGES`, `PageOrder.addToOrder` |
| R11 | **One live shell at a time on the radio**, by construction: a screen is records | `docs/ARCHITECTURE.md` §11 |
| R12 | **A rekey is still possible** when a shrink cannot reach a chunk already in flight; bounded to once per 30 s | `resizeToLink(force = true)`, `RESIZE_FLOOR_MS` |
| R13 | **A stuck companion radio holds the command queue**; a raw send waits at most 2 s and a refused attempt is given back rather than counted | `send_raw_within`, `refuseSeq` |

### Every timing figure, and what it is derived from

A number that has to be right on a one-hop link and on a 28-hop one cannot be a constant. Each figure
below is either **derived** (a formula over airtime, hops or the radio's own report) or **policy**
(a decision no measurement can make), and nothing in the radio path is an unexplained literal.

| Figure | Value | Basis |
|---|---|---|
| One record's airtime | 603 ms | **Measured** at 62.5 kHz / SF7 / CR5 (172 B record) |
| `rto_initial` | 6 airtimes per hop | **Derived** — MeshCore's own direct-send budget (`DIRECT_SEND_PERHOP_FACTOR`); 101 s at 28 hops |
| `rto_max` | 40 airtimes | **Derived** — one record's worth of wait before the ladder's cap |
| `ack_delay_ms` | 2 airtimes, floor 150 ms | **Derived** — long enough for an ack to ride the next data record, short enough never to be the delay (`6.164`) |
| fast retransmit floor | 1 airtime | **Derived** — a record cannot have arrived before its own transmission finished |
| `max_attempts` | 5 | **Policy** — MeshCore's own figure for a direct send |
| `window` | 8 records | **Policy** — the L2 credit |
| `handshakeRetryFor` | 8 s + 2 s a hop | **Derived** — one round trip: the firmware's forward delay is up to 2 airtimes a hop |
| `handshakeWaitMs` | `retry << 3` | **Derived** — the ladder's own sum, including the last re-ask's window (`6.172`) |
| `handshakeVerdictMs` | 30 s + 2 s a hop | **Derived** — the point at which "handshaking" becomes "no answer came" |
| `answerDeadlineMs` (attach, create, list, resync, history) | base + 2 s a hop | **Derived** — the same forward-delay figure |
| `routeRepairMs` | 2 × 6 airtimes a hop, floor 20 s | **Derived** — twice the first copy's budget (`6.163`) |
| `silenceFailureMs` | 60 s + 3.6 s a hop, cap 300 s | **Derived** — the ARQ's own first timeout, plus the route |
| `route_stale` (host) | max(60 s, 2 × hops × airtime) | **Derived** — a route is dead when a round trip over it is late (`6.174`) |
| `PEER_ROUTE_RETRY` | 15 s | **Policy** — how often a pathless host asks |
| `ROUTE_REPLY_FLOOR` | 5 s | **Policy** — the floor that stops a radio becoming a repeater of itself |
| `ps` carrier silence | max(75 s, 3 × rto) | **Derived** — three attempts is the ARQ's own verdict |
| `LINK_GIVE_UP_MS` | 10 min | **Policy**, and named as such — a radio cannot know whether its owner turned round (`6.173`) |
| `REBUILD` ladder | 2 s doubling, 300 s cap | **Policy** — full jitter, so two ends never meet in lockstep |
| `SEND_RESULT_TIMEOUT_MS`, `REQUEST_ANSWER_MS`, `RAW_WINDOW_WAIT_MS` | 10 s / 2 s / 1.5 s | **Local** — the companion's own answer window over serial, never the air |
| `PATH_RETRY_MS`, `PATH_REFRESH_MS`, `IDLE_TICK_MS`, `STATS_WATCH` | 10 s / 60 s / 30 s / 20 s | **Local** — serial reads, no airtime |
| `ROUTE_TRUST_MS` / `ROUTE_FRESH_MS` / `FAILED_ROUTE_HOLD_MS` | 60 s / 120 s / 120 s | **Policy** — the community's path-gating window, and how long a bad path is remembered |
| `MAX_HOPS` | 63 | **Firmware** — a 64-byte path field, one byte a hop |

### Deliberately not changed, with the reason

Four findings from the 2026-11-10 audits are decisions, not omissions. Each is recorded here so a
later reader does not re-open it as a defect.

| Finding | Why not |
|---|---|
| **Candidate sets and path rotation on the first retransmission** — keep N paths and try the next when one fails | The record limit is derived from the path in use, so a rotation would have to re-size per attempt or size for the largest candidate, and every attempt on a new path would be a record the peer may never have heard of. The proof rule (6.188) already stops a working route being unseated, and a failed session clears the path and asks once — one flood, one transmission for us. The complexity is worse than the failure it fixes |
| **One shared wall-clock budget for session death** | The phone's silence verdict (`60 s + 3.6 s × hops`, 161 s at 28 hops) already fires long before the host's five-attempt ladder, and the host accepts a fresh `msg1` while a session is live, so the phone is the authority in practice. Making it formal changes the protocol for no behavioural gain |
| **Retrying the close record** | A close is a courtesy: the peer's own silence bound ends the session anyway, and a close that arrives after the peer has already rebuilt lands on a dead index and is dropped. A retry would cost air to say something the receiver has already decided |
| **`max_attempts = 5` as a count rather than a time budget** | With the ceiling above the route's round trip (6.177) five attempts is `5 × 6 × airtime × hops` — bounded and derived. A wall-clock budget would be prettier and would produce the same five attempts at every route this protocol can carry |

### By design, not a fault

A scope is never invented (ADR-0033); ldmux keeps no contacts (ADR-0030); session records are never
flooded, because a raw custom packet is delivered only on a direct route (ADR-0035); five pages, one
radio shell, and no log on disk.

### Listing copy

Short description: a terminal for a shell on your own Linux machine, over tailnet or radio.

Full description: ldmux is a terminal for a shell that runs on a Linux machine you own, not on

## Appendix B: open decisions

None of these are defects. Each is a decision that changes what ships.

1. ~~The radio tuple the app compiles in.~~ **Closed 2026-11-06.** The deployed radio runs
   910.525 MHz, 500 kHz, SF7, CR5, which is the app's compiled default, so a fresh install
   reaches this host with no tuple work. The code also carries the host's tuple, so a
   deployment that differs is one press to match. The physical tuple stays a deployment
   choice; the app adopts what the radio reports.
2. Whether the host radio is a shipped feature. The daemon owns it when `LDMUX_MESH_SERIAL` is
   set, and nothing installs or provisions it, so today the route works for an operator who
   reads `docs/ARCHITECTURE.md` section 11 and not for a new user. The in-app side now says
   what the hardware must be; the host side still has no command that finds and names the port.
3. The upload keystore and the store assets, which are the operator's to supply.
4. Whether the mesh link carries a heartbeat while a phone is attached. Today it does not, so a
   phone that vanishes without a `Detach` keeps its shell claim until the link is rebuilt or
   the daemon restarts, and the phone cannot tell a dead host from a quiet one. A record every
   five minutes costs ≈12 of the hour's 255 records at 500 kHz/SF7 and ≈4 % of the
   budget at 62.5 kHz. Open because it trades an invariant ("an idle screen costs nothing")
   against a liveness guarantee.

## Appendix C: known unfinished

- A desk window displaced by a mesh claim is not covered by a test. The daemon sends the notice
  and the same message is proven for a WebSocket claim, but the mesh variant has no test.
- A shell created from a phone is recorded with `createdBy` set to `phone`, and rows keep their
  actions across an app restart because of it. There is no test that asserts that round trip.
- Dictation depends on the device's speech recogniser, which may be cloud-based. The app says
  so, and nothing here can change it.
- Multi-hop is implemented in both directions and unit-tested, and has never run on air. The phone
  reads the host's advert path, the host reads the phone's after a 36-byte route hint, and each
  replies along the reverse. `ARCHITECTURE.md` section 11 says what is proven and what is not: the
  first on-air run with a repeater between two radios out of earshot is what would prove it.
- **Airtime: the host enforces 1 % itself, with the firmware's own limiter as the backstop.** The
  serial carrier computes the hour's allowance from the tuple (`budget_per_hour`,
  `mesh_serial.rs:714`) and publishes it as `Status.ops_left_this_hour`; the mesh loop takes that
  upward only (`mesh.rs:821`) and hands it to `Arq::poll` as `records_left`, which caps **new data**
  and never gates an ack, a retransmission or a close (`arq.rs` "4. The close, last, once"). The
  firmware's limiter is real but is not the 1 % a European band requires: `Dispatcher` refills a
  duty-cycle budget of `1/(1 + getAirtimeBudgetFactor())` and `getAirtimeBudgetFactor()` returns 1.0
  (`Dispatcher.cpp:26,34-36`), which is a **50 %** duty cycle. So the host's own meter is the one that
  matches the band, and the firmware's is a ceiling far above it.
- A spawned window is scoped, but its **workspace placement** (i3/sway/hyprland) is only
  exercised by `desktop_e2e`; nothing asks for a workspace from a phone today, so the adapter
  is carried, not used.
- RTL and split screen are unverified (3.6). Dark mode is not a question (dark-only, with the bar
  icons pinned light) and font scale is handled (`heightIn`, not a fixed height).
- Nothing outside this machine builds the Android artifact (1.7).
